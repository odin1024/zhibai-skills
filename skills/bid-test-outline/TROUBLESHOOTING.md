# 异常处理

## 输入类问题

| 现象 | 处理 |
|---|---|
| 只给了项目名，没有被测对象 | 追问：设备/系统清单、指标要求、使用场景；先给通用框架 |
| 招标文件条款编号混乱 | 按出现顺序重编并在表内注明「原条款：X」 |
| 依据标准给错编号 | 指出并纠正，同时提示「以招标文件指定版本为准」 |
| 指标要求互相矛盾（如招标要求 10G，产品标称 8G） | 按招标要求写测试项，同时标注「当前产品不满足，需确认型号」 |
| 要求覆盖的范围超出项目实际 | 拆分「本期范围 / 后续扩展」，不把未来需求写进本期大纲 |

## 设计类问题

| 现象 | 处理 |
|---|---|
| 某个测试项写不出判定准则 | 说明该项尚未定义清楚，建议删除或改为「观察项」，不写「功能正常」凑数 |
| 性能项缺少测试条件 | 补默认值（1518B、60s、RFC2544）并标注「建议条件，请按实际调整」 |
| 安全测试项与等保控制项对不上 | 按 GB/T 22239-2019 控制项编号重新映射，标注对应关系 |
| 用例步骤依赖未提供的环境 | 在「前置条件」中标为待准备，并进环境检查清单 |
| 缺陷等级判断有争议 | 按「是否阻断验收」定 P0/P1，其余按影响面定 P2/P3 |

## 输出类问题

| 现象 | 处理 |
|---|---|
| 大纲太长，超出投标页数 | 正文放矩阵 + 3—5 个代表用例，完整用例转附录 |
| 表格列太多，Word 里排版错乱 | 拆成两张表：用例表（横向）+ 判定表（纵向） |
| 编号不连续 | 统一规则 TC-类别-两位序号，重新编号并说明 |
| 输出混入方案性描述 | 明确「只做测试设计，不写产品方案」，删掉方案段落 |

## 流程类问题

| 现象 | 处理 |
|---|---|
| 做到一半断了 | 贴回已完成的矩阵，说明「从 XX 类继续」 |
| 被测对象变更 | 只改受影响的测试项，其余保留，版本号 +0.0.1 |
| 甲方临时加验收项 | 追加到矩阵末尾并标「变更项」，注明提出时间与提出方 |
| 时间不够，只能交框架 | 优先给 P0 项的六要素，P1 项给矩阵和判定准则，P2 项列名即可 |

## 拒绝执行

1. **要求编造测试记录或测试数据**——验收造假
2. **要求设计攻击路径、提供利用代码**——超出测试设计范围
3. **要求承诺「保证通过验收」**——无法保证
4. **要求把未测项写成已测**——同上
5. **要求删除已发现的缺陷记录**——隐瞒问题
