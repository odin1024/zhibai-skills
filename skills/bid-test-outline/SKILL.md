## 一分钟看懂

你告诉它「测什么、按什么标准、给谁看」，它还你一份能直接进标书或验收会的测试大纲。

```
输入：
  项目：某单位安全设备采购，含防火墙 2 台、入侵检测 1 台、日志审计 1 台
  依据：招标文件第三章、GB/T 22239-2019
  场景：投标技术方案附件 / 交付验收
  ↓
输出：
  ① 测试目标与范围（测什么、不测什么）
  ② 测试环境（拓扑、设备清单、工具、账号）
  ③ 测试项矩阵（5 类 × N 项，带优先级）
  ④ 每个用例的六要素（前置/步骤/预期/判定/记录/异常）
  ⑤ 缺陷分级与通过标准
  ⑥ 记录表模板（可直接打印）
```

核心差别：**每个测试项都必须有可量化的判定准则**。没有判定准则的测试大纲，在评标现场等于没写。

## 什么时候用

| 场景 | 典型说法 |
|---|---|
| 投标技术方案要附测试大纲 | 「招标文件要求提供测试方案，帮我写一份」 |
| 项目交付前要定验收标准 | 「甲方要我们先交测试大纲，再进场」 |
| 安全设备采购要证明能测 | 「防火墙、IDS 这些怎么设计测试项」 |
| 等保测评前想自测一遍 | 「按等保三级要求，先自己测一轮」 |
| 外包软件验收没有标准 | 「开发说做完了，我们不知道怎么验」 |

## 什么时候不该用

- **要写参数响应表**（逐条应答招标参数）→ 用「参数响应表生成器」
- **要出正式的第三方检测报告**→ 需要 CMA/CNAS 实验室，本技能只做测试设计
- **要做渗透测试实施**（实际打点、拿权限）→ 属于安全服务，需授权与专业工具
- **要写性能调优方案**→ 本技能只设计怎么测，不负责调优

## 三步上手

**第一步**：说清被测对象——设备型号/系统名称/模块清单，以及项目类型（采购、集成、软件开发）

**第二步**：给依据——招标文件条款、国家标准号、合同验收条款，没有就说明「按行业通用做法」

**第三步**：说用途——投标附件（要体现专业度、可演示）、交付验收（要可执行、可签字）、内部自测（要快）

## 核心工作流

### 第一步：划测试边界

先明确三件事，否则大纲一定写成大而空：

1. **测什么**：列出被测对象清单（设备型号、软件模块、接口）
2. **不测什么**：明确排除项（如「不含机房环境测试」「不含第三方系统对接」）——写清不测什么，反而显得专业
3. **谁来看**：投标评委看专业度，甲方看可执行性，内部看效率。同一份大纲，侧重点不同

### 第二步：搭测试项矩阵

按五个维度铺开，每个维度先列粗项，再决定深度：

> 七类设备（防火墙/IDS/WAF/堡垒机/日志审计/终端/软件系统）的现成测试项与指标参考，见 `references/测试项库.md`。先挑项，再补六要素。

| 维度 | 典型测试项 | 优先级 |
|---|---|---|
| 功能测试 | 核心功能、配置生效、策略命中、告警上报、报表导出 | P0 |
| 性能测试 | 吞吐量、时延、并发连接、新建速率、资源占用 | P0（有指标要求时） |
| 安全测试 | 身份鉴别、访问控制、审计日志、传输加密、漏洞扫描 | P0（安全设备必测） |
| 兼容性测试 | 浏览器、操作系统、数据库、国产化环境、上下架设备对接 | P1 |
| 可靠性测试 | 连续运行、主备切换、断电恢复、异常注入、日志不丢 | P1 |

优先级定义：**P0 = 不通过则整体不验收**；P1 = 影响评分或需整改；P2 = 建议改进。

### 第三步：写六要素用例

每个测试项必须写全六件事，缺一条就是不可执行：

```
用例编号：TC-FUNC-001
测试项名称：访问控制策略命中验证
前置条件：设备已上电、管理口已配置 IP、已创建测试用安全域
测试步骤：
  1. 登录管理界面，进入「策略配置 → 安全策略」
  2. 新建策略：源 10.10.1.0/24 → 目的 10.20.1.10，服务 HTTP，动作 允许
  3. 保存并下发，确认策略状态为「已生效」
  4. 从 10.10.1.20 发起 HTTP 访问 10.20.1.10
预期结果：访问成功，策略命中计数 +1
判定准则：命中计数从 0 变为 1，且会话表存在对应会话 → 通过；计数不变 → 不通过
记录要求：截图（策略列表 + 命中计数 + 会话表）
异常处理：若策略下发失败，记录错误码，检查设备版本是否支持该功能
```

**六要素里最容易漏的是「判定准则」和「异常处理」**，而这两项恰好是评委判断专业度的地方。

### 第四步：定判定准则

判定准则必须满足三条：**可观测、可量化、可复现**。

| 类型 | 不合格写法 | 合格写法 |
|---|---|---|
| 功能 | 「功能正常」 | 「策略命中计数由 0 增至 1，会话表出现对应会话」 |
| 性能 | 「性能良好」 | 「64/512/1518 字节包长下，吞吐 ≥ 标称值 90%，丢包率 ≤ 0.001%，测试时长 60s」 |
| 安全 | 「安全性高」 | 「使用 X 扫描器全端口扫描，高危漏洞 0 个，中危 ≤ 2 个且 72 小时内整改」 |
| 兼容 | 「兼容主流浏览器」 | 「Chrome/Edge/Firefox 最新版 + 360 极速模式，核心页面无 JS 报错、布局无错位」 |
| 可靠 | 「运行稳定」 | 「连续运行 72h，无重启、无进程退出，内存增长 ≤ 5%，日志无丢包」 |

### 第五步：出记录表与执行计划

- **记录表**：每类测试一张，列固定为「用例编号 / 测试项 / 预期结果 / 实际结果 / 结论 / 测试人 / 日期 / 备注」
- **执行计划**：按依赖排序（先环境搭建 → 功能 → 性能 → 安全 → 可靠性），标注每项预计耗时
- **准入准出**：进入测试的条件（环境就绪、版本冻结）、结束测试的条件（P0 全通过、P1 通过率 ≥ 90%）

## 五类测试的专项打法

### 功能测试

- 每个功能至少三条用例：**正常路径 / 边界值 / 异常路径**
- 安全设备必测：策略增删改查、策略命中、策略冲突优先级、NAT、日志上报、配置备份恢复
- 软件必测：核心业务流程端到端、权限边界、并发操作、数据一致性

### 性能测试

性能项离开测试条件就没有意义，必须写清五件事：

1. **包长/数据量**：64 / 512 / 1518 字节，或并发用户数、记录条数
2. **测试时长**：60s / 300s / 24h
3. **并发模型**：长连接/短连接、新建速率、并发数
4. **测试工具**：RFC2544 打流仪型号、JMeter 版本、脚本参数
5. **判定口径**：取平均值还是峰值、是否含建链时间

### 安全测试

分两层，别混在一起：

- **产品自身安全**：默认口令、弱口令、未授权访问、越权、日志完整性、传输加密、已知漏洞
- **安全功能有效性**：攻击检出率、误报率、阻断时延、规则库更新时效

判定要给出样本量与统计口径（如「用 100 条测试样本，检出 ≥ 95 条，误报 ≤ 5 条」）。

### 兼容性测试

国内项目必须覆盖国产化环境：麒麟/统信操作系统、达梦/人大金仓数据库、东方通/宝兰德中间件、奇安信/360 浏览器。漏了国产化，技术方案会被认为不了解国内项目实际。

### 可靠性测试

- 连续运行：72h / 7 天，看内存、句柄、日志
- 主备切换：断主链路，测切换时间与业务中断时长
- 断电恢复：直接断电，测重启后配置是否丢失
- 异常注入：端口 down、磁盘满、时钟跳变、证书过期

## 三个真实样例

### 样例 1：安全设备采购（投标附件）

**输入**：某单位采购下一代防火墙 2 台，招标要求「提供完整测试方案，含功能、性能、可靠性测试」，技术方案附件用。

**输出节选**

| 编号 | 测试项 | 判定准则 | 优先级 |
|---|---|---|---|
| TC-PERF-01 | 整机吞吐量 | 1518B 包长、RFC2544 双向、60s，吞吐 ≥ 10Gbps 且丢包率 ≤ 0.001% | P0 |
| TC-PERF-02 | 新建连接速率 | 新建速率 ≥ 8 万/秒，持续 60s，失败率 ≤ 0.1% | P0 |
| TC-FUNC-05 | 策略冲突优先级 | 同一流量命中「允许」与「拒绝」两条策略时，按优先级高者执行，命中计数正确 | P0 |
| TC-REL-02 | 双机热备切换 | 断开主设备上行链路，备机切换 ≤ 3s，已建立会话中断 ≤ 5s | P1 |

**说明**：投标场景的判定准则要「看起来能验」，数字比形容词有说服力。评委不会真的去测，但会看你会不会测。

### 样例 2：软件交付验收

**输入**：某管理系统交付，含登录、工单、报表三模块，甲方要求先交测试大纲。

**输出节选**

```
用例编号：TC-FUNC-LOGIN-02（边界值）
前置条件：系统已部署，测试账号 test01 存在
测试步骤：
  1. 打开登录页
  2. 输入 test01 + 错误口令，连续 5 次
  3. 第 6 次输入正确口令
预期结果：前 5 次提示「用户名或口令错误」，第 6 次提示「账号已锁定，请 15 分钟后重试」
判定准则：锁定策略在第 5 次失败后触发，锁定期间正确口令也无法登录 → 通过
异常处理：若未锁定，记录为 P1 缺陷（安全策略未生效）
```

**说明**：边界值和异常路径是验收时最容易被漏测的，也是上线后最容易出问题的。

### 样例 3：等保测评前自测

**输入**：三级系统上线前自测，依据 GB/T 22239-2019。

**输出节选**

| 编号 | 对应控制项 | 测试项 | 判定准则 |
|---|---|---|---|
| TC-SEC-01 | 8.1.4.1 身份鉴别 | 口令复杂度与定期更换 | 口令 ≥ 8 位且含三类字符，90 天强制更换，历史 5 次不重复 |
| TC-SEC-02 | 8.1.4.3 安全审计 | 审计记录完整性 | 覆盖每个用户，记录日期时间/用户/事件类型/结果，留存 ≥ 6 个月 |
| TC-SEC-03 | 8.1.4.4 入侵防范 | 最小安装原则 | 开放端口清单与实际扫描一致，无多余服务 |

**说明**：自测大纲要能直接映射到测评项，否则测评时还要重做一遍。

## 反模式

| 反模式 | 为什么不行 | 正确做法 |
|---|---|---|
| 只列测试项，不写判定准则 | 无法判定通过与否，验收时扯皮 | 每项必须有可量化准则 |
| 步骤写成「检查功能是否正常」 | 不同人执行结果不同，不可复现 | 写到「点哪里、输入什么、看哪个指标」 |
| 没有前置条件 | 换个人就跑不起来 | 写清环境、账号、数据准备 |
| 性能测试不写测试条件 | 数字没有可比性 | 包长、时长、并发、工具全写 |
| 只测正常路径 | 上线后异常场景全暴露 | 每个功能至少加边界值和异常路径 |
| 兼容性只写 Windows | 国内项目大量国产化环境 | 补麒麟/统信、达梦、国产浏览器 |
| 缺陷不分级 | 出问题不知道先修哪个 | P0-P3 + 处理时限 |
| 没有记录表 | 验收时无法留痕签字 | 附录给模板 |
| 测试范围写成「全面测试」 | 等于没划边界 | 明确列出不测什么 |
| 投标大纲写得像内部文档 | 评委看不懂专业度 | 加依据条款映射、加判定准则、加记录表 |

## 常见问题

**Q：投标用的测试大纲，需要写多细？**
比交付用的粗一档，但判定准则不能省。评委看三样：有没有依据条款、有没有量化判定、有没有记录表。这三样齐了，专业度就够。

**Q：没有招标文件，只有一句话需求，能写吗？**
能，但会先追问：被测对象是什么、有没有指标要求、给谁看。信息不足时输出「通用框架 + 待填项」，不硬编数字。

**Q：性能指标写多少合适？**
按产品标称值的 80%—90% 写判定线，留出测试环境损耗。写满标称值，现场跑不出来会很难看。

**Q：测试环境和生产环境不一致怎么办？**
在大纲里单列「环境差异说明」和「差异对结果的影响评估」，这比假装一致更专业。

**Q：能不能直接生成 Excel？**
输出的是表格结构，可粘贴到 Excel。需要公式或数据验证的话，建议用平台的表格技能二次处理。

**Q：等保自测大纲能直接用于测评吗？**
不能替代。测评由具备资质的测评机构执行，自测大纲的作用是提前发现问题、准备证据材料。

## 错误处理

| 输入情况 | 处理 |
|---|---|
| 只给「帮我写测试大纲」 | 追问三件事：测什么、依据什么、给谁看 |
| 被测对象不明确 | 先列「待确认清单」，按最常见形态给一版草案 |
| 指标要求缺失 | 判定准则处留「建议值」并标注来源（行业惯例/产品标称） |
| 依据标准给错（如把 22239 写成 22240） | 指出并纠正，同时提示「请以招标文件指定版本为准」 |
| 要求「写一份能保证通过的测试大纲」 | 拒绝承诺结果，只保证设计合规、可执行 |
| 要求生成虚假测试记录 | 拒绝，说明验收造假的合同与法律风险 |

## 稳定性与一致性

- 同一被测对象，测试项编号规则稳定（TC-类别-序号），不会这次 TC-FUNC-01、下次 F-001
- 分批生成时，每批结尾给出「已覆盖维度 / 待补维度」
- 中断后可凭已生成的矩阵续写用例，不需重来
- 不联网，不调用外部测试工具

---

## 能力边界

**能做**：测试范围划定、测试项矩阵、六要素用例、判定准则、缺陷分级、记录表、执行计划。

**不能做**：
- 不替代第三方检测机构的正式检测报告
- 不实施渗透测试，不提供攻击工具与利用代码
- 不保证被测系统一定通过
- 不编造测试数据与测试记录

**一条底线**：判定准则写不出来，说明这个测试项还没想清楚——宁可删掉，也不要写「功能正常」四个字凑数。
