# 常见问题

## 关于场景

**Q：投标用的和交付用的，有什么区别？**
投标用的偏「证明我们会测」：要有依据条款映射、量化判定、记录表，让评委看懂专业度。交付用的偏「照着能跑」：步骤要细到点击位置，前置条件要写全，异常要给出处理路径。同一套东西，深度不同。

**Q：没有招标文件，只有一个项目名，怎么办？**
会先追问三件事：被测对象是什么、有没有指标要求、给谁看。信息不够时给「通用框架 + 待填项」，不会硬编指标。

**Q：软件项目还没有需求文档，能写测试大纲吗？**
能写框架，但功能测试项会大量留空。建议先有需求或原型，否则测试项只能按「登录/权限/CRUD」这类通用项铺，价值有限。

**Q：集成项目涉及多个厂商，测试怎么组织？**
按「单设备测试 → 接口联调 → 端到端业务」三层写。单设备各自测，联调测协议和时序，端到端测业务闭环。三层都要有判定准则。

## 关于判定准则

**Q：判定准则到底要写多细？**
细到「换一个没参与过的人，照着你写的步骤能得出同样的结论」。做不到这一点，就是不够细。

**Q：性能指标写多少不会被现场打脸？**
按产品标称值的 80%—90% 写判定线，并注明测试环境（如「单机、无其他业务流量」）。写满标称值，现场跑不出来很难看。

**Q：功能测试一定要写异常路径吗？**
一定要。正常路径只能证明「能用」，异常路径才能证明「可靠」。验收后出问题的，八成在异常路径上。

**Q：安全测试要测漏洞扫描吗？**
产品类项目建议测，但要写清扫描器名称、版本、扫描策略和漏洞库日期——不同工具结果差异很大，不写清楚没法复现。

**Q：可靠性测试 72 小时太久，能缩短吗？**
可以，但要在文档里说明「本次测试时长 24h，未覆盖长周期内存泄漏风险」。缩短可以，假装测过不行。

## 关于输出

**Q：能直接生成 Word 或 Excel 吗？**
输出的是结构化文本和表格，可粘贴到 Word/Excel。需要自动排版、目录、页眉页脚，建议配合平台的文档技能。

**Q：测试项太多，投标文件放不下怎么办？**
正文放矩阵和代表性用例，完整用例放附录或「另册」。投标文件通常有页数限制，学会分级呈现。

**Q：记录表需要签字吗？**
正式验收的记录表需要测试人、复核人、甲方代表签字。投标阶段只需给模板，不需要真记录。

## 关于边界

**Q：能帮我设计渗透测试的攻击路径吗？**
不能。本技能只做测试设计（测什么、怎么判定），不提供攻击实施方法与利用代码。

**Q：能保证按这个大纲测就一定能过验收吗？**
不能。大纲保证的是「测试设计合规、可执行」，通过与否取决于被测系统本身。

**Q：能帮我补一份测试记录吗？**
不能。编造测试记录属于验收造假，涉及合同违约与法律责任。
