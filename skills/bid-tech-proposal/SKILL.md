# 投标技术方案生成器

## 这个技能解决什么

技术标丢分，绝大多数不是「写得不够漂亮」，而是三件很具体的事：

1. **没按评分办法写。** 评委手里有一张评分表，逐项打分。方案里写了大量产品特性，却没有一处能对应到「方案完整性 15 分」的四个采分点，评委找不到给分依据。
2. **漏项。** 评分细则里有一条「提供应急预案与演练计划，2 分」，方案里根本没这一章。不是写得差，是没写。
3. **三份材料互相打架。** 参数响应表里写「吞吐量 ≥ 10 Gbps」，技术方案里写「8 Gbps」，测试大纲里测的是「5 Gbps」。任何一处不一致，轻则被要求澄清，重则被认定为响应不实。

这个技能把顺序倒过来：**先拆评分表，再定章节，最后才写正文**。每一章都必须能回答「它对应评分表哪一条、评委凭什么给分、依据在哪个附件」。

它同时管住一条底线：**不替投标人编造事实**。资质、业绩、产品型号、检测报告、案例数据，没有提供就写【待确认】，进待补清单，绝不生成一个看起来很合理的数字。

---

## 什么时候用，什么时候不用

| 场景 | 用不用 |
|---|---|
| 有招标文件（哪怕只是一段评分办法），要写技术方案 / 技术标 | **用** |
| 已有一版方案，想查漏项、查口径不一致 | **用** |
| 要把技术要求逐条映射到章节 | **用** |
| 只有一句「帮我写个智慧园区方案」，没有招标文件、没有评分办法 | **先问**：按「通用方案骨架」写，并明确标注这版不针对任何评分表 |
| 商务标、报价表、资格证明文件、法定代表人授权书 | **不用**，超出范围 |
| 要代填资质、编案例、造检测报告 | **不做**，见「能力边界」 |
| 招标文件明确禁止 AI 辅助编制，或要求特定软件格式签章 | **不用**，提示用户按招标文件要求人工处理 |

## 输入清单

**必需（缺一项就先问，不要脑补）**

| 输入 | 说明 |
|---|---|
| 评分办法 / 评分细则 | 技术部分的评分项、分值、采分点描述。这是全技能的驱动源 |
| 技术要求 / 采购需求 | 招标文件技术规格章节、功能清单、设备清单或服务范围 |
| 项目基本信息 | 项目名称、标的类别（货物 / 服务 / 工程）、交付或实施周期 |

**强烈建议提供**

| 输入 | 说明 |
|---|---|
| 废标条款与实质性要求 | ★ / ▲ 条款、否决投标的情形、格式与签章要求 |
| 投标人已有资料 | 产品彩页、检测报告清单、同类项目业绩、资质证书、团队名单 |
| 另外两份交付物 | 参数响应表、测试大纲（若已用同系列技能生成，直接贴来即可） |
| 交付格式要求 | 章节编号规则、字数或页数上限、是否需要单独成册 |

**输入形式**：粘贴文本、表格（可保留行列结构）、扫描件转文字均可。扫描件识别不清的地方标【识别不清】，不要猜字。

## 六步工作流

### S1　拆招标文件：建三张底表

把原文拆成互不混淆的三张表，后面所有章节都从这三张表长出来。

| 底表 | 字段 | 用途 |
|---|---|---|
| A 评分点表 | 编号、评分项原文、分值、采分点拆解、对应章节（待填）、状态 | 驱动章节骨架 |
| B 技术要求表 | 编号、要求原文、性质（★/▲/一般）、量化指标、对应方案要素 | 驱动方案内容 |
| C 约束表 | 废标条款、格式要求、签章、页数、禁止事项、交付清单 | 驱动最后的自查 |

**拆解规则**

- 一个评分项若含多个采分点（例如「方案完整性，含需求理解、架构设计、实施组织、风险控制，共 15 分」），必须拆成多行，一行一个采分点；分值能明确就分，不能明确就写「15 分（含 4 项，未细分）」，**不要自行平均分配分值**。
- ★ / ▲ 条款单独标记，并在 C 表里写清后果（按招标文件原文，不自行推断「一定废标」）。
- 招标原文照抄进「原文」列，不做润色，便于逐条核对。

### S2　建评分点覆盖矩阵

对 A 表每一行，填四件事：

| 评分点编号 | 评分项原文 | 分值 | 落在哪一章 | 论证方式 | 佐证材料 | 状态 |
|---|---|---|---|---|---|---|
| S-03-02 | 应急预案与演练计划 | 2 | 第 7 章 7.2 | 流程 + 频次 + 责任人 + 记录表 | 附件 5《应急演练记录模板》 | 待补材料 |

- **论证方式**只能从这五类里选：流程说明 / 架构与拓扑 / 量化指标与验证方法 / 组织与人员安排 / 历史材料佐证。选不出来，说明这个采分点没理解，回到 S1 重拆。
- **状态**四选一：已覆盖 / 部分覆盖 / 待补材料 / 不适用（须写明理由）。
- 矩阵必须做到「每个采分点至少一行」，最后统计覆盖率；有「待补材料」要单独列清单交用户，不能悄悄略过。

### S3　倒推章节骨架

**按评分点倒推，不套通用模板。** 排序规则：

1. 分值高的评分项排前面，独立成章；
2. 多个评分项共用同一论证材料的，合并成一章，但矩阵里仍分别对应；
3. 招标文件的格式要求（如「技术方案须含 1 项目理解、2 总体设计……」）优先于上面的排序；
4. 每章标注：对应评分点编号、预计页数、需要用户提供哪些材料。

骨架输出后先给用户确认，再写正文。**不要一上来就写两万字**——骨架错了，正文全白写。

### S4　逐章成文：五段式

每章固定五段，缺一段就是漏项：

| 段 | 写什么 | 常见错误 |
|---|---|---|
| ① 需求理解 | 复述这个评分点对应的招标要求，说明本项目为什么需要它 | 抄一遍招标原文当作自己的理解 |
| ② 设计依据 | 招标条款编号、适用的标准/规范、投标人已有能力 | 堆一堆和本章无关的标准 |
| ③ 方案内容 | 架构、组成、流程、角色、步骤，具体到可执行的粒度 | 写成产品彩页，全是形容词 |
| ④ 可验证指标 | 每条指标给「指标值 + 验证方法 + 验证阶段」 | 只有指标值，没法验收 |
| ⑤ 佐证索引 | 附件编号、页码、材料名称、当前是否已具备 | 写「详见附件」但不给编号 |

**语言要求**：陈述句、可核对、不用「业界领先」「完全满足」「自主研发领先水平」这类没有判据的表述；不确定的写【待确认：<需要什么>】。

### S5　三份交付物一致性校验

若用户同时给了参数响应表和测试大纲（或用了同系列技能），逐项比对下面六类口径，输出校验表：

| 校验项 | 从哪取 | 不一致怎么处理 |
|---|---|---|
| 量化指标（吞吐量、并发、可用率、响应时间…） | 参数响应表 / 技术方案 / 测试大纲 | 以招标要求为准，列出三处取值，标注需统一的那一处 |
| 设备型号与数量 | 设备清单 / 方案架构 / 测试用例 | 列出差异，不自行改数 |
| 术语与命名 | 三份全文 | 统一成招标文件用词 |
| 章节与条款引用 | 三份交叉引用 | 修正编号，或标注【引用待核】 |
| 标准与依据 | 方案依据 / 测试依据 | 统一版本表述，提示核对现行有效版本 |
| 偏离状态 | 参数响应表 | 方案里不得把「负偏离 / 待确认」写成「满足」 |

**这是本技能最容易带来实际价值的一步**：三份材料口径不一致是标书审核最常被打回的原因。

### S6　交付前自查

按下面清单逐条过，输出自查结果，不要只说「已完成」：

- [ ] A 表每个采分点在矩阵里都有对应行，覆盖率 100%
- [ ] 每章五段式齐全，④ 的每条指标都有验证方法
- [ ] 所有【待确认】已汇成待补清单，并注明找谁要
- [ ] 所有附件索引有编号，未具备的材料标「待补」
- [ ] 无编造的资质、业绩、型号、检测数据、案例
- [ ] 无「完全满足」「业界领先」等无判据表述（除非招标原文要求且确有依据）
- [ ] ★ / ▲ 条款逐条有响应，C 表约束全部检查过
- [ ] 一致性校验表已出，无未解释的差异
- [ ] 章节编号、页数、格式符合招标文件要求

## 输出规范

一次交付六份成果，按此顺序排列，每份都带标题和表格头：

**① 招标文件拆解表**（A 评分点表 / B 技术要求表 / C 约束表）
**② 评分点覆盖矩阵**（含覆盖率统计与待补材料清单）
**③ 技术方案章节骨架**（章号、标题、对应评分点、预计页数、需补材料）
**④ 逐章正文**（五段式，可直接粘贴进标书）
**⑤ 一致性校验表**（六类口径，逐项列出差异与处理建议）
**⑥ 废标与扣分风险清单**（风险项、依据原文、当前状态、建议动作、责任方）

**表格一律用 Markdown 表格**，便于贴进 Word / Excel。所有「原文」列保留招标文件的原始措辞。

### 模板：评分点覆盖矩阵

```
| 编号 | 评分项原文 | 分值 | 章节 | 论证方式 | 佐证材料 | 状态 |
|---|---|---|---|---|---|---|
| S-01-01 | （照抄） | （照抄） | 第 3 章 3.1 | 架构与拓扑 | 附件 2 拓扑图 | 已覆盖 |
| S-01-02 | （照抄） | （照抄） | 第 3 章 3.2 | 量化指标与验证方法 | 附件 3 检测报告【待补】 | 待补材料 |
```

### 模板：逐章五段式

```
## 第 N 章　<章节标题>　（对应评分点：S-xx-xx，<分值> 分）

### N.1 需求理解
招标文件「<条款号>」要求 <原文要点>。本项目 <结合项目情况说明为什么需要>。

### N.2 设计依据
- 招标文件 <条款号>；
- <标准/规范名称与编号>（引用前须核对招标文件与现行有效版本）；
- 投标人已有能力：<用户提供，未提供则写【待确认】>。

### N.3 方案内容
<架构/组成/流程/角色/步骤，分点写，每点可核对>

### N.4 可验证指标
| 指标 | 指标值 | 验证方法 | 验证阶段 |
|---|---|---|---|
| <指标名> | <值或【待确认】> | <怎么测、用什么测、判定准则> | 到货验收 / 实施 / 终验 |

### N.5 佐证索引
| 附件编号 | 材料名称 | 页码/位置 | 是否具备 |
|---|---|---|---|
```

## 三个真实示例

### 示例 1：评分办法拆出隐藏采分点

**输入**：某政务云安全设备采购，评分办法技术部分有一条——
> 「技术方案完整性 15 分：方案包含需求理解、总体架构、部署实施、运维服务、应急预案，每项 3 分。」

**输出节选（覆盖矩阵）**：

| 编号 | 评分项原文 | 分值 | 章节 | 论证方式 | 状态 |
|---|---|---|---|---|---|
| S-01-01 | 需求理解 | 3 | 第 2 章 | 流程说明 | 已覆盖 |
| S-01-02 | 总体架构 | 3 | 第 3 章 | 架构与拓扑 | 待补材料（拓扑图） |
| S-01-03 | 部署实施 | 3 | 第 5 章 | 组织与人员安排 | 已覆盖 |
| S-01-04 | 运维服务 | 3 | 第 6 章 | 流程说明 + 量化指标 | 已覆盖 |
| S-01-05 | 应急预案 | 3 | 第 7 章 | 流程说明 + 记录表 | 已覆盖 |

**关键动作**：一条 15 分的评分项被拆成 5 个独立采分点，每个点单独成节并标注分值。若按「技术方案完整性」笼统写一章，评委很难逐项给满。同时把「拓扑图」列入待补清单，而不是自己画一个不存在的网络拓扑。

### 示例 2：标准引用怎么处理才不犯错

**输入**：等保测评服务招标，技术要求写「依据等保 2.0 相关标准开展测评」。

**输出节选（N.2 设计依据）**：

> - 招标文件「第三部分 采购需求 2.1」；
> - 常见依据标准包括《信息安全技术 网络安全等级保护基本要求》GB/T 22239-2019、《信息安全技术 网络安全等级保护测评要求》GB/T 28448-2019、《信息安全技术 网络安全等级保护安全设计技术要求》GB/T 25070-2019、《信息安全技术 网络安全等级保护测评过程指南》GB/T 28449-2018、《信息安全技术 网络安全等级保护定级指南》GB/T 22240-2020 等；
> - **引用前必须逐条核对招标文件指定的版本，并以全国标准信息公共服务平台公布的现行有效状态为准**；本技能不保证标准号的最新性，也不代替招标文件的指定版本；
> - 测评机构资质、测评师名单：附件 6【待补：由投标人提供】。

**关键动作**：给出可核对的标准清单，同时把「版本核对」和「资质材料」明确交给用户，不冒充权威结论。

### 示例 3：信息严重不足时

**输入**：用户只发来一句「帮我写个数据中心安全建设的技术方案，明天要交」。

**输出**：不编造招标要求。先回一张「最小信息清单」：

| 缺什么 | 为什么必需 | 没有时的降级做法 |
|---|---|---|
| 评分办法 | 决定章节和分值权重 | 按通用骨架写，并在首页醒目标注「本版未针对任何评分表，正式投标前必须按评分办法重排」 |
| 技术要求与设备清单 | 决定指标和数量 | 只写架构原则与流程，所有指标写【待确认】 |
| 投标人资质与业绩 | 决定佐证索引 | 全部列进待补清单 |

然后交付一版「通用骨架 + 五段式模板正文」，正文里用【待确认】占位，绝不给一个看起来完整、实则全是编造数字的方案。

## 判定规则（硬规则，不可自行放宽）

1. **评分点来自招标原文。** 不自行增加评分项，不把多个采分点合并成一行，不自行分配未细分的分值。
2. **不编造事实。** 资质、业绩、案例、产品型号、检测数据、人员姓名、报告编号、页码，未提供一律【待确认】。
3. **不把「待确认」写成「满足」。** 参数响应表里的负偏离 / 待确认，在技术方案里必须保持一致口径。
4. **标准引用可核对。** 给出名称与编号时附一句版本核对提示；招标文件指定了版本，以招标文件为准。
5. **量化指标三件套。** 指标值、验证方法、验证阶段缺一不可；验证方法要与测试大纲的测试用例对得上。
6. **一章对一评分点。** 章节骨架里每章标注对应编号；无对应评分点的章节标注「招标格式要求」或「建议删减」。
7. **原文与方案分开。** 招标原文照抄进表的「原文」列，方案正文是自己的表述，不复制原文冒充方案。
8. **不用无判据表述。** 「完全满足」「业界领先」「零风险」「100% 可靠」除非招标原文要求且有材料支撑，否则不写。

## 反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 拿通用模板改个项目名就交 | 评委按评分表打分，模板里的章节和采分点对不上 | 先出 A 表，再倒推骨架 |
| 把产品彩页整段贴进方案 | 讲的是产品有什么，不是这个项目怎么落地、怎么验证 | 五段式的 ③ 写「本项目怎么做」，④ 给可验证指标 |
| 为了「显得完整」编一个吞吐量数字 | 一旦被要求提供检测报告，就是响应不实 | 写【待确认：需产品检测报告第 X 页】 |
| 评分项里 5 个采分点合并成一节 | 评委找不到逐项给分依据，容易只给一半分 | 一采分点一小节，标题里点明关键词 |
| 三份交付物各写各的 | 指标口径不一致会被质疑响应真实性 | 出一致性校验表，逐项对齐 |
| 堆一长串标准号充专业 | 与本章无关，或版本已失效，反而暴露不严谨 | 只列本章真正用到的，并附版本核对提示 |
| 把「★ 条款」当成普通要求 | 实质性条款漏响应可能直接影响投标有效性 | 在 C 表单列，逐条检查并标注后果（按招标原文） |
| 交付时不说还缺什么 | 用户以为可以直接封标，实际附件全没准备 | 每版都附待补材料清单和自查结果 |

## 能力边界与底线

- **不做**：商务报价、资格文件、法定代表人授权、签章、投标文件装订与上传、代投标。
- **不编造**：资质、业绩、产品型号、检测报告、案例数据、人员信息、任何可核验的事实。
- **不保证**：中标结果、评分结果、招标文件的解释权、标准号的现行有效性、平台格式兼容性。
- **不替代**：法务/合规审核、招标代理答疑、造价与报价决策。涉及歧义条款，建议按招标文件约定提出澄清。
- **一条底线**：宁可交一版带满【待确认】的骨架，也不交一版读起来漂亮但事实无据的方案。标书上的每个数字都可能被要求举证。

## 与同系列技能的衔接

| 技能 | 负责什么 | 本技能怎么衔接 |
|---|---|---|
| 参数响应表生成器 `bid-param-response` | 招标参数逐条响应、偏离判定、★ 条款覆盖 | 取它的「量化指标 / 型号 / 偏离状态」做一致性校验 |
| 测试大纲生成器 `bid-test-outline` | 测试项矩阵、六要素用例、判定准则 | 取它的「验证方法 / 判定准则」填进五段式的 ④ |
| 本技能 `bid-tech-proposal` | 评分点倒推章节、逐章成文、佐证索引 | 输出一致性校验表，把三份材料锁到同一口径 |

三者共用同一份招标技术要求，**不要各写一套指标**。若用户只用了本技能，在 ④ 里给出验证方法建议，并提示「正式交付前建议与测试大纲对齐」。

## 自检

交付前对照「S6 交付前自查」逐条打勾，并在末尾附一句：

> 本版共拆出 N 个采分点，覆盖 N 个；待补材料 N 项；一致性差异 N 处；未解释差异 0 处。

有任何一项没算清楚，就不要写「已完成」。
