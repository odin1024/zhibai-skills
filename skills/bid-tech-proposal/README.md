# 投标技术方案生成器

把招标文件的**评分办法**拆成逐条可核对的采分点，倒推章节骨架，再逐章写成能直接放进标书的技术方案正文。

不是模板库，也不是「帮我写两万字」。核心是三件事：**不漏评分点、不编造事实、三份技术材料口径一致**。

---

## 一分钟上手

把下面这些贴给 Agent：

```
用 bid-tech-proposal 写技术方案。
【评分办法】（粘贴招标文件技术评分表）
【技术要求】（粘贴技术规格 / 采购需求章节）
【项目信息】项目名称、货物/服务/工程、实施周期
【已有资料】（可选：产品彩页、检测报告清单、业绩、资质、团队）
【另外两份交付物】（可选：参数响应表、测试大纲）
```

Agent 会先给 **招标文件拆解表 + 评分点覆盖矩阵 + 章节骨架**，等你确认骨架，再展开逐章正文。

> 顺序很重要。骨架没确认就写正文，一旦评分项理解错了，两万字全白写。

---

## 会得到什么

| # | 交付物 | 作用 |
|---|---|---|
| ① | 招标文件拆解表 | 评分点表 A / 技术要求表 B / 约束表 C，原文照抄便于核对 |
| ② | 评分点覆盖矩阵 | 每个采分点落在哪一章、怎么论证、要什么附件、还缺什么 |
| ③ | 技术方案章节骨架 | 章号、标题、对应评分点编号、预计页数、需补材料 |
| ④ | 逐章正文 | 五段式：需求理解 / 设计依据 / 方案内容 / 可验证指标 / 佐证索引 |
| ⑤ | 一致性校验表 | 与参数响应表、测试大纲对齐六类口径，列出差异 |
| ⑥ | 废标与扣分风险清单 | 风险项、招标原文依据、状态、建议动作、责任方 |

每版末尾附**待补材料清单**和**交付前自查结果**，不会让你以为「可以直接封标了」而其实附件一份没准备。

## 一个最小示例

**输入**

> 评分办法：技术方案完整性 15 分，含需求理解、总体架构、部署实施、运维服务、应急预案，每项 3 分。
> 项目：某单位安全设备采购，货物类，30 天内完成部署。

**输出节选（覆盖矩阵）**

| 编号 | 评分项原文 | 分值 | 章节 | 论证方式 | 佐证材料 | 状态 |
|---|---|---|---|---|---|---|
| S-01-01 | 需求理解 | 3 | 第 2 章 | 招标条款对照表 | 招标文件条款号 | 已覆盖 |
| S-01-02 | 总体架构 | 3 | 第 3 章 | 架构与拓扑 | 附件 2 拓扑图 | 待补材料 |

**正文节选（五段式）**

```
### 3.4 可验证指标
| 指标 | 指标值 | 验证方法 | 验证阶段 |
|---|---|---|---|
| 设备吞吐 | 【待确认：需检测报告页码】 | 按测试大纲 T-03 施加标称负载并记录转发速率 | 到货验收 |
```

注意那个【待确认】：没有检测报告就不会出现一个「看起来很合理」的数字。

```bash
git clone https://github.com/odin1024/zhibai-skills.git
cp -r zhibai-skills/skills/bid-tech-proposal ~/.claude/skills/
```

```bash
cd bid-tech-proposal && python scripts/verify.py
```

## 配套技能

| 技能 | 负责 | 关系 |
|---|---|---|
| `bid-param-response` 参数响应表生成器 | 招标参数逐条响应、偏离判定、★ 条款 | 提供指标与偏离状态 |
| `bid-test-outline` 测试大纲生成器 | 测试项矩阵、六要素用例、判定准则 | 提供验证方法 |
| `bid-tech-proposal`（本技能） | 评分点倒推章节、逐章成文 | 输出一致性校验表，锁住三份口径 |

三者共用同一份招标技术要求，**别各写一套指标**。

---

## 能力边界（请认真看）

- 不编造资质、业绩、产品型号、检测数据、案例、人员姓名；没有就标【待确认】。
- 不做商务报价、资格文件、签章、投标上传，不代投标。
- 不保证中标、不预测得分、不解释招标文件、不保证标准号现行有效。
- 涉及歧义条款，建议按招标文件约定走澄清流程，不要按本技能的推断执行。

**底线：宁可交一版带满【待确认】的骨架，也不交一版读起来漂亮、事实却无据可查的方案。**
