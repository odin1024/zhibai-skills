# 实战踩坑库

> 全部来自批量开发、打包、发布、同步、核查过程中的真实故障记录，已脱敏。
> 每条按「现象 → 原因 → 修法 → 预防」写，目的是让你不用再踩一遍。

---

## 坑 1　slug 被占，发布返回 409

- **现象**：`409 SLUG_OWNED_BY_OTHER`，发布直接失败。
- **原因**：slug 全平台唯一；此前只用模糊搜索看过，没做精确查重。有些同名条目来自外部导入，也会出现在搜索索引里。
- **修法**：换一个语义独特的 slug，同步调整 displayName；写查重脚本按 `slug` 精确匹配，并核对 `owner_name`。
- **预防**：把查重放进选题阶段。**注意**：自己已上线的技能也会被查成「已占用」，必须按作者区分，否则会误判成全部不可用。

## 坑 2　中文文件名静默丢失

- **现象**：批量推送 44 个文件，回显成功，仓库里少了 6 个中文命名的参考文档。
- **原因**：HTTP 请求路径未 percent-encode，非 ASCII 文件名在构造 URL 时抛错；批量脚本吞掉单文件异常继续跑。
- **修法**：`quote(path, safe="/")`；补推时只推缺失文件。
- **预防**：所有批量写入脚本都要输出「成功 / 失败 / 跳过」逐项统计，失败数不为 0 时退出非零码。**别只看命令退出码 0**。

## 坑 3　打包把子目录平铺了

- **现象**：包里出现根目录的 `verify.py`，而不是 `scripts/verify.py`。
- **原因**：打包函数对相对路径取了 `name`，丢掉父目录。
- **修法**：`map_name()` 先判断 `len(rel_path.parts) > 1`，是子目录就保留完整相对路径，只有根级文件才做前缀映射。
- **预防**：打包后列一次包内清单，和源目录逐项比对。

## 坑 4　references 命名与包内结构不一致

- **现象**：本地用 `references_规则清单.md`，用户装完发现不在 `references/` 目录。
- **原因**：本地扁平命名（方便管理）与平台包内目录结构没做映射。
- **修法**：打包时把 `references_` / `templates_` 前缀映射成 `references/` / `templates/` 子目录。
- **预防**：本地命名约定、打包映射、SKILL.md 里的引用路径三者写在同一份规范里；verify.py 对这种命名报 WARN 即可，验收记录写明理由。

## 坑 5　发布限流 429

- **现象**：连续发布第二个技能返回 429。
- **原因**：同一账号两次发布需要间隔，实测约 45 秒起。
- **修法**：发布脚本改成顺序执行，默认间隔 50 秒；不要用并发抢时间。
- **预防**：批量发布前先算总时长，把限流写进脚本默认值，并在日志里打印等待时间。

## 坑 6　HTTP 201 不等于上线

- **现象**：发布返回 201、拿到 skillId，但站内搜不到。
- **原因**：返回体里有内容审核、图标审核、安全扫描、review 等多个 `pending` 状态，索引要等审核后才进。
- **修法**：把「发布成功」和「已可见」分开记录；用精确 slug 查搜索索引，查不到就标「审核中」。
- **预防**：交付报告里写清两个状态，别向用户宣告「已上线」。

## 坑 7　搜索补位噪声导致误判赛道

- **现象**：搜一个长尾词返回 30 条，前几条是几百万下载的头部技能，以为赛道被垄断。
- **原因**：搜索接口会用热门条目补位；真正相关的只有开头若干条。
- **修法**：按 `slug / displayName / description` 是否含关键词筛相关性，按 `owner_name` 去重，重算头部下载。
- **预防**：任何「竞品强度」「是否收录」结论都基于精确匹配，不基于模糊搜索前几条。核查收录时优先用全量分页 + `fullName` 精确匹配。

## 坑 8　首次发布 tags 为空

- **现象**：技能上架后标签区空白，长尾搜法全部漏掉。
- **原因**：payload 构造时没把 frontmatter 的 tags 带进去。
- **修法**：`build_payload()` 显式加 `tags` 字段；同时把 keywords 也带上。
- **预防**：发版前用 dry-run 打印完整 payload，逐字段核对。

## 坑 9　分类填了英文 key 却不生效

- **现象**：`categoryIds` 传了英文值，平台分类仍然不对。
- **原因**：部分平台会自动判定分类，传值只是参考。
- **修法**：名称和 summary 里写进真实分类词，不依赖分类字段猜。
- **预防**：把分发权重放在名称、摘要、tags 上，分类字段只当辅助。

## 坑 10　AI 生成图标带水印

- **现象**：图标右下角有生成工具水印，缩略图里很显眼。
- **原因**：直接用了生成图，没有后处理。
- **修法**：可用纯色采样覆盖，但更稳的做法是**改用代码手绘矢量**：渐变底 + 白色大色块 + 简洁符号 + 底部暗角；先出 96px 预览确认可辨。
- **预防**：图标纳入 P4 验收项，问一句「这个能放进作品集吗」。别用占位图。

## 坑 11　自检脚本把自己报成危险代码

- **现象**：verify.py 扫到 `scripts/` 里的检测规则字面量，报「含敏感调用」。
- **原因**：规则库里为了识别危险命令，写了这些词本身；扫描器不区分「规则字符串」和「真实调用」。
- **修法**：敏感字面量用分段拼接，运行时等价但静态不命中；拼接段要带 `r` 前缀，否则 `\s`、`\.` 会触发语法警告；自检时排除脚本自身。
- **预防**：写检测器类技能时，先跑一遍「扫自己」，再扫别人。

## 坑 12　空仓库没有 main 分支

- **现象**：`PUT /contents` 全部失败。
- **原因**：新建的空仓库还没有默认分支，contents API 无处可写。
- **修法**：建仓时 `auto_init: True`，然后轮询 branches 直到 main 就绪再推。
- **预防**：把「仓库存在」和「分支就绪」当成两个状态，不要假设前者包含后者。

## 坑 13　GitHub App 无建仓权限

- **现象**：`create_repository` 返回 `403 Resource not accessible by integration`。
- **原因**：集成型令牌权限范围不含建仓。
- **修法**：改用 classic PAT，`public_repo` scope 足够建公开仓库、写文件、设 topics。
- **预防**：动手前先确认凭据类型与 scope，别在错误凭据上反复重试。

## 坑 14　事实性错误藏在细节里

- **现象**：文档里写了「微信设置 → 隐私 → 添加我的方式」（路径已变）、「转账后 10 分钟黄金时间」（无可靠依据）、「口播 220–260 字」（与实际节奏不符）。
- **原因**：凭记忆写细节，没逐条核对。
- **修法**：路径按当前版本实际走一遍改成「设置 → 朋友权限 → 添加我的方式」；无依据的时限改成定性表述「资金停留时间很短，越早越有止付机会」；字数按实测节奏调整。
- **预防**：所有路径、电话、时限、标准号列成「需核对项」表，发布前逐条打勾。**拿不准就写定性，不写精确数字。**

## 坑 15　冷启动零下载被误判为失败

- **现象**：上线两小时，下载 0–3、星标 0，怀疑选题错了。
- **原因**：搜索按下载排序，新技能天然排不上；这不是内容问题，是分发问题。
- **修法**：记录基线，7 天后复测；优先迭代名称与摘要，配合站外导流；不要靠批量发同质技能冲量。
- **预防**：把「上线」和「起量」当成两个阶段，分别设指标。

## 坑 16　同步脚本每次都刷一遍 commit

- **现象**：只改了一个文件，全量同步却产生几十个无意义提交。
- **原因**：同步脚本无条件 PUT 每个文件。
- **修法**：先 GET 远端内容，与本地比对，相同则跳过；保留 `--only-missing` 用于失败补推。
- **预防**：任何「同步」类脚本都要有幂等设计。

## 使用方式

- 每次开工前扫一遍和自己当前阶段相关的坑（P0 看 1、7；P5 看 2–6、8–9、12–13；P6 看 6、7、15）。
- 遇到新坑，按同样四段格式追加到本文件，并同步更新 P3 的验收记录模板里相关检查项。
- 不要把「修法」当成通用结论：平台接口会变，以当前实测返回为准。
