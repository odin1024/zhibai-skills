# Skill 开发上架工厂

## 这个技能解决什么

大多数人以为「写完 SKILL.md 就做完了」。实际跑通一批技能之后会发现，写文档大概只占三成工作量，剩下的七成在这些地方：

- **选题**：你想起的名字，用户根本不搜。同一件事换个说法，流量能差三个数量级。
- **分发**：名字、摘要前 80 字、标签、图标，决定了平台能不能把你推到搜索结果里。
- **工程**：包内目录结构、中文文件名编码、slug 全局唯一、发布限流、审核状态，任何一处出错都是白跑一趟。
- **冷启动**：新技能 0 下载、0 星标，在按下载排序的搜索里几乎不会出现。不主动导流和复核，就永远停在原地。

这个技能把整个过程拆成**七个阶段、每阶段有明确交付物和闸门**，并且把批量开发中真实踩过的坑写进来——不是理论，是能直接照着避开的工程记录。

一条原则贯穿始终：**不刷量、不抄袭、不编造数据**。技能的价值最终由「它能不能解决一个真实问题」决定，标题和标签只是让需要它的人找得到。

## 什么时候用，什么时候不用

| 场景 | 用不用 |
|---|---|
| 想做新技能，还没定题 | **用**，从 P0 开始 |
| 已有想法，想验证值不值得做 | **用**，重点跑 P0 |
| 写完 SKILL.md，准备上架 | **用**，从 P3 开始 |
| 技能上线后没人搜到、没下载 | **用**，重点跑 P6 |
| 要批量做一批技能、想统一规范 | **用**，全套 + 模板复用 |
| 只想让人帮忙润色一段提示词 | **不用**，太重了 |
| 想刷下载、刷星标、批量注册马甲占词 | **不做**，见「能力边界」 |
| 开发的是带后端服务、需要密钥与用户数据的应用 | **部分适用**：P0–P3 可用，安全与合规需另做专门评审 |

## 七阶段流水线

> 每阶段都有一份交付物。**没过闸门就不要进下一阶段**，返工成本会指数级上升。

### P0　选题验证（最该花时间的一步）

**四问**，任何一问答不上来就先别动手：

| 问 | 怎么答 | 答不上来的后果 |
|---|---|---|
| 用户会用什么词搜它？ | 用平台搜索接口实测 3–5 个同义词，看真实结果 | 名字起得再好，没人搜 = 不存在 |
| 这个词下面真实头部是多少？ | 记录相关条目的下载量，**剔除补位噪声** | 误判蓝海/红海 |
| 我比现有产品多提供什么？ | 一句话说清差异化，说不清就别做 | 变成第 N 个同质技能 |
| 能不能和已有技能串成工作流？ | 画出串联关系 | 单品难积累，成包才有复利 |

**关键词实测的正确姿势**（很容易做错）：

1. 搜索接口常会**补位**——返回一堆和关键词无关的热门技能凑数。只看前几条会把 600 万下载的头部误当成竞品。
2. 判定相关性要看 `slug / displayName / description` 是否真含关键词，并核对 `owner_name`；不相关的头部一律剔除。
3. 用**精确匹配**核查某个 slug 是否已被占用；只靠模糊搜索会漏。
4. 同一需求的不同说法要分别测：实测中「防骗」与「诈骗识别」两个词，头部下载差了一千倍以上。

**P0 交付物**：选题卡（目标词、同义词实测表、真实竞品头部、差异化的三句话、可串联的技能）、**候选 slug 查重结果**。

> 闸门：至少有一个「有真实搜索量 + 竞品不强 + 我能做得更好」的词；候选 slug 未被他人占用。

### P1　规格设计

先定死三件事，再写正文：

- **frontmatter 字段**：`slug / displayName / version / summary / license / name / description / author / category / iconUrl / tags / keywords / target_users / trigger`。少了哪个，后面发布或自检都会卡。
- **触发条件**：写 5–8 条用户真实会说的话，不要写「当用户需要时」这种空话。
- **能力边界**：明确「不做什么」。这一项决定技能会不会给出越界结论，是专业度最直观的体现。

**P1 交付物**：规格表（字段值 + 触发条件清单 + 边界清单 + 目标用户）。

### P2　内容生产

**SKILL.md 七段式**（缺一段就会显得单薄）：

| 段 | 内容 |
|---|---|
| ① 这个技能解决什么 | 讲真实痛点，不讲行业趋势 |
| ② 什么时候用 / 不用 | 表格，含明确的「不做」 |
| ③ 工作流 | 分步骤，每步有输入、动作、产出 |
| ④ 输出规范 | 模板 + 表格头，能直接贴走 |
| ⑤ 三个真实示例 | 输入 → 输出节选 → 关键动作说明 |
| ⑥ 判定规则与反模式 | 硬规则 + 「为什么错 / 正确做法」两列 |
| ⑦ 能力边界与底线 | 一条底线，不写套话 |

**references 分层**：主文档只放「每次都要读」的工作流；领域知识库、案例库、规则表拆到 `references/` 独立文件，由主文档按需引用。判据是：**这段内容是不是每次调用都需要**。不是就拆出去。

**事实准确性**：涉及路径、电话、时限、标准号、法规的表述逐条核对；拿不准就写成「以官方最新口径为准」并标注需核对，绝不编一个精确数字。

**P2 交付物**：SKILL.md、README.md（一分钟上手）、FAQ.md（≥10 条）、TROUBLESHOOTING.md（≥8 类异常）、references/ 深度库、`_meta.json`。

### P3　质量闸门

用 38 项清单逐组验收（详见 `references/质量清单.md`），并用 `scripts/verify.py` 做机器自检：

```bash
cd <技能目录> && python scripts/verify.py
```

verify.py 至少检查：必需文件齐全、frontmatter 字段完整且合法、slug/version/目录名三者一致、关键章节存在、参考库存在、脚本里没有会被平台安全扫描误判的字面量。

**闸门**：0 个 FAIL。WARN 可以有，但要逐条判断能不能接受（例如 `references_xxx.md` 的下划线命名，若打包脚本会映射成 `references/`，就是可接受的）。

### P4　上架物料

| 物料 | 规则 |
|---|---|
| 名称 displayName | **就是用户会搜的那个词**，一个字都不多；权威后缀（专家 / 生成器 / 教练）比「助手」更有感知价值 |
| summary 前 80 字 | 塞进 8–12 个触发词：核心需求词、同义词、典型输入、典型产出 |
| tags / keywords | 首次发布就要写进 payload，别发完再补；tags 覆盖类别词，keywords 覆盖长尾搜法 |
| 图标 | 手绘矢量、渐变底、白色大色块、96px 下仍可辨；不要带水印、不要把缩略图直接放大 |
| 分类 | 按平台实际生效的值填；有的平台会自动判定，别依赖英文 key 猜 |
| changelog | 每次发版写清改了什么，便于用户和审核理解 |

> 图标是用户看到的第一眼，敷衍的图标会直接拉低点击。**做成能放进作品集的精度，不是占位图。**

**P4 交付物**：上架物料卡（名称 / 摘要 / tags / keywords / 图标 / 分类 / changelog）+ 图标文件。

### P5　打包与上架

**包内结构**：根级放 SKILL.md、README.md、FAQ.md、TROUBLESHOOTING.md、_meta.json；`scripts/` 和 `references/` 保持子目录。**常见错误**：打包时把 `scripts/verify.py` 平铺到根目录，或用 `references_xxx.md` 命名却没有映射成 `references/xxx.md`。

**发布前四查**：

1. **slug 查重**：全平台唯一，被别人占用会返回 409。用精确匹配查，不要靠模糊搜索。
2. **密钥隔离**：API Key 放环境变量或 `.env`，写进 `.gitignore`，绝不进技能包。
3. **限流**：同一账号两次发布通常要间隔 45 秒以上；批量发布脚本默认留 50 秒，别用并发硬冲。
4. **审核状态**：发布成功（HTTP 201）不等于立刻能被搜到，返回里常有内容审核、图标审核、安全扫描、review 多个 pending 字段。**要区分「发布成功」和「已上线可见」**。

**中文文件名**：走 HTTP API 推送时，路径必须 percent-encode，否则 ASCII 编码错误会导致部分文件静默失败。推送后要按文件数核对，别只看「命令没报错」。

**P5 交付物**：技能 zip、发布回执（skillId / slug / 版本 / 审核状态）、线上可见性核查记录。

### P6　数据复核与迭代

上架后别急着做下一个，先复核四件事：

| 复核项 | 怎么做 | 常见误判 |
|---|---|---|
| 能不能被搜到 | 用**精确 slug** 查，别用模糊词 | 搜索补位返回一堆热门技能，误以为「已收录」 |
| 索引状态 | 区分「审核 pending」与「已进索引」 | 发布 201 就宣告上线 |
| 下载 / 星标 | 记录基线，7 天后复测 | 把 0 下载当成失败，其实只是上线时间太短 |
| 名称匹配 | 看用户搜核心词时自己排第几 | 只看自己搜全名能命中，就以为分发没问题 |

**冷启动是真实存在的死锁**：按下载排序时，0 下载的新技能很难靠站内搜索起量。可控的动作只有三个——把名称对齐精确搜索词、把物料做扎实、从站外（公众号、GitHub、社区）导流。**不存在「多发几个就能起来」的捷径**，批量注册同质技能只会稀释账号。

迭代优先级：先改名称和摘要（成本最低、影响最大），再补内容深度，最后才考虑开新技能。

## 输出规范

每次对话按用户所处阶段给对应交付物，**不要一上来把七阶段全倒给用户**。

### 模板：选题卡

```
【目标词】xxx        【同义词实测】
| 说法 | 相关条目数 | 真实头部下载 | 判断 |
|---|---:|---:|---|
【真实竞品】名称 / owner / 下载 / 它没做什么
【我的差异化】三句话
【可串联】已有技能 A → 本技能 → 已有技能 B
【候选 slug】a-b-c（精确查重：可用 / 被 xxx 占用）
【结论】做 / 不做 / 换词，理由
```

### 模板：上架物料卡

```
slug:            displayName:
version:          category:
summary（≤80字触发词）:
tags:             keywords:
图标文件:          changelog:
发布前自查: slug✅ 密钥✅ 限流✅ 审核状态✅
```

### 模板：交付闸门结果

```
质量清单：38 项，通过 __ / 不适用 __ / 未通过 __
verify.py：FAIL __ / WARN __
未通过项与处理：逐条列出
结论：可上架 / 需返工（列返工项）
```

## 三个真实示例

以下来自批量开发并上架多个技能时的工程记录，均已脱敏。

### 示例 1：slug 被占，发布直接 409

**现象**：给「简历诊断」类技能起了 `resume-doctor`，发布返回 `409 SLUG_OWNED_BY_OTHER`。

**原因**：slug 全平台唯一，且不同作者可能已在搜索索引里用了同名（有的是外部导入的条目）。此前只用模糊搜索看过，没做精确查重。

**修法**：改成 `resume-checkup`，同时把 displayName 调成更贴合搜索词的名字；发布前加一个查重脚本，并检查 `owner_name` 是否是自己——**自己的已上线技能也会被查成「已占用」，必须按作者区分**。

**预防**：把 slug 查重写进 P0 闸门。另有一类情况：某赛道里同一个 slug 出现多个不同作者的条目，此时更安全的做法是换一个语义独特、不易撞车的名字，而不是抢热词。

### 示例 2：44 个文件推完，6 个静默失败

**现象**：同步 GitHub 仓库后回显「成功」，但仓库里少了 6 个中文命名的参考文档。

**原因**：HTTP 请求里的路径没做 percent-encode，非 ASCII 文件名在构造 URL 时报错；批量脚本吞掉了单文件异常继续跑。

**修法**：路径用 `quote(path, safe="/")`；每文件记录状态并汇总「成功 / 失败 / 跳过」，失败数不为 0 就退出非零码；补推时只推缺失文件。

**预防**：批量写入类脚本一律要有**逐项结果 + 总数核对**，不能只看「命令退出码 0」。

### 示例 3：以为「搜不到」，其实是补位噪声

**现象**：搜索某个关键词返回 30 条，前几条是几百万下载的头部技能，误以为该赛道已被垄断。

**原因**：搜索接口会用热门条目补位。真正相关的只有前面若干条，后面全是无关键词的噪声。

**修法**：按 `slug / displayName / description` 是否含关键词筛相关条目，再按 `owner_name` 去重，重新统计真实头部。实测某安全审计赛道的相关竞品是 9 个，最高约 3,900 下载——既不是无人区，也远不是百万级垄断。

**预防**：所有「竞品强度」「是否收录」的结论，必须基于**精确匹配 + 作者维度**，不能基于模糊搜索的前几条。

## 判定规则（硬规则）

1. **名称就是搜索词。** 不加「智能」「AI 时代」这类稀释核心词的前缀；权威后缀优先于「助手」。
2. **先查重再开发。** 候选 slug 未经精确查重，不进入 P1。
3. **0 FAIL 才能上架。** 质量清单和 verify.py 的 FAIL 必须清零。
4. **事实可核对。** 路径、电话、时限、标准号、数据，拿不准就标注需核对，不编精确值。
5. **能力边界必写。** 没有「不做什么」的技能不算完成。
6. **示例必须真实。** 三个示例要有输入、输出节选和关键动作说明，不能是「用户问 A，技能答 B」。
7. **图标不敷衍。** 96px 缩略下可辨、无水印、与名字语义相关。
8. **发布 ≠ 上线。** 必须复核索引可见性、审核状态，并把两者分开记录。
9. **不刷量、不抄袭、不编造下载数据。**
10. **密钥不进包。** `.env` 进 `.gitignore`，发布前扫一遍文件清单。

## 反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 先写两万字 SKILL.md，再想叫什么 | 名字决定能不能被搜到，返工代价最大 | P0 先做选题与查重 |
| 拿通用模板改几个词就发 | 同质技能没有差异化，也不会有人装 | 回答「我比现有产品多提供什么」 |
| 把全部知识塞进一个 SKILL.md | 每次调用都读，噪声大、难维护 | references 分层，主文档只放工作流 |
| 摘要写成产品宣传语 | 搜索匹配不到长尾触发词 | 前 80 字塞 8–12 个真实搜法 |
| 图标用生成图直接放大 | 水印、糊、和名字没关系 | 手绘矢量 + 小尺寸验证 |
| 批量并发发布抢时间 | 触发限流 429，反而更慢 | 顺序发布，间隔 ≥45 秒 |
| 看到 HTTP 201 就宣告上线 | 审核 pending 时用户根本搜不到 | 分开记录「发布成功 / 已可见」 |
| 用模糊搜索前几条判断竞品 | 补位噪声会把热门条目当竞品 | 精确匹配 + owner 去重 |
| 一个月发十个同质技能冲量 | 稀释账号、0 下载互相压权重 | 先迭代名称与内容，再考虑新品 |
| 为了通过检查改检查脚本 | 问题还在，只是看不见了 | 修根因，或明确记录可接受的 WARN 及理由 |

## 能力边界与底线

- **不做**：刷下载 / 刷星标 / 批量注册马甲占词 / 抄袭他人技能内容 / 编造平台数据。
- **不保证**：上架必过审核、搜索排名、下载量、平台接口不变、分类取值长期有效。接口与规则以平台当前文档和实测返回为准。
- **不替代**：法务合规审查、内容安全评估、真实用户调研。涉及医疗、金融、法律、未成年人等敏感领域，需另做专业评审。
- **不碰密钥**：不读取、不打印、不上传任何凭据明文；只描述「应该放哪里」。
- **一条底线**：宁可少上一个技能，也不上一个自己都不愿意装给自己用的技能。

## 自检

交付前逐条打勾，并在末尾写一句：

> 当前阶段：P__；闸门通过：是/否；未通过项：__；下一步：__。

闸门没过就写「否」，不要写「基本完成」。
